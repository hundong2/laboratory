## 한눈에 보기

AI가 코드 생성 시간을 줄이면 전체 개발 리드타임의 병목은 계획, 검토, 승인, 배포, 운영으로 이동한다. AI-native SDLC는 각 단계를 없애는 접근이 아니라, **사람이 판단할 지점은 명시적인 게이트로 남기고 반복 작업과 증거 생성을 자동화하는 순환형 개발 체계**다.

```text
intent.md → spec.md → plan.md → 코드·테스트
    ↑                              ↓
운영 이상·incident ← 배포·관측 ← 검토·승인
```

각 단계의 종료 산출물은 다음 단계의 입력이며 Git 이력은 요청, 생성, 검토, 승인에 대한 감사 추적이 된다. 이때 중요한 원칙은 다음과 같다.

1. 에이전트가 읽을 수 있는 정책과 실행 가능한 검증을 함께 둔다.
2. 모델의 판단이 필요한 일과 결정론적 검사를 분리한다.
3. 자율성은 환경과 위험도에 따라 계층화한다.
4. 에이전트는 운영 게이트 앞까지 준비할 수 있지만 중요한 승인은 사람이 맡는다.
5. 운영 사고와 반복 실수는 다시 명세·평가 사례로 환류한다.

## 기초 개념

### SDLC

Software Development Life Cycle은 아이디어가 요구사항, 설계, 구현, 시험, 배포, 유지보수를 거쳐 운영 가치가 되는 전체 과정이다. AI-native라는 말은 각 단계에 챗봇을 하나씩 붙인다는 뜻이 아니라, 단계 간 전달 형식과 통제 증거를 에이전트가 처리할 수 있게 바꾼다는 뜻이다.

### 커밋된 산출물

대화창의 결론은 검색과 감사가 어렵다. 반면 버전 관리되는 `intent.md`, `spec.md`, `plan.md`, 코드 diff, 테스트 결과, 리뷰·사고 기록은 사람과 에이전트가 함께 읽고 다음 자동화를 시작할 수 있다.

### 조언형 통제와 강제형 통제

- 지침 파일과 스킬은 바람직한 행동을 설명하는 **조언형 통제**다.
- 테스트, 린터, 권한, 샌드박스, 훅, 브랜치 보호는 위반을 기계적으로 차단하는 **강제형 통제**다.
- 보안·규제 조건은 설명만으로 보장하지 말고 강제형 통제로 뒷받침해야 한다.

### 평가와 피드백 루프

일반 테스트는 제품 코드가 기대대로 동작하는지 확인한다. 에이전트 평가는 프롬프트, 지침, 스킬, 훅 또는 모델이 바뀌어도 작업 품질이 유지되는지 확인한다. 실제 작업 20~50개로 시작하고 운영 사고를 회귀 사례로 추가하는 방식이 제안된다.

## 6단계 운영 모델

| 단계 | 핵심 산출물 | AI-native 변화 | 사람의 책임 |
| --- | --- | --- | --- |
| Plan | `intent.md` | 원 제안자의 말에서 문제·성과·제약을 구조화 | 오해 수정, 가치와 범위 승인 |
| Design | `spec.md` | 정책·보안·UX 지침을 적용해 요구와 설계를 함께 작성 | 상충 정책과 위험 결정 |
| Build | `plan.md`, 코드, 테스트 | 읽기 전용 계획 후 구현, 저장소 지침·스킬·훅 활용 | 계획 승인, 병렬 작업 조정 |
| Test | 검증 로그, eval 결과 | 세션 자체 피드백과 에이전트 설정 회귀 평가 | 합격 기준과 독립 검증 설계 |
| Deploy | 리뷰 기록, 릴리스 기록 | 계층화된 자동 리뷰와 승인 훅, 제한된 CI/CD 실행 | 위험 수용과 운영 승인 |
| Maintain | incident `intent.md`, 회고·eval | 결정론적 탐지 후 진단·제안·사전 승인 런북 실행 | 경보 분류, 조치 승인, 정책 조정 |

### 1. Plan

아이디어를 처음 들은 사람이 에이전트와 대화해 문제, 기대 결과, 영향 사용자·시스템, 제약, 미해결 질문을 `intent.md`로 만든다. 제품 책임자가 내용을 고치고 승인한 뒤 커밋한다. 형식화가 빨라져도 문제 선택과 우선순위는 자동 결정하지 않는다.

### 2. Design

승인된 의도에 조직의 브랜드, 보안, 규제, UX 정책을 적용해 `spec.md`를 만든다. 정책 충돌과 불확실한 영역을 숨기지 않고 표시하는 것이 핵심이다. 지침 버전, 입력 의도, 결과 명세를 함께 남기면 무엇을 근거로 설계했는지 추적할 수 있다.

### 3. Build

구현 전 읽기 전용 분석으로 변경 파일, 순서, 위험, 검증 방법을 포함한 `plan.md`를 승인한다. 저장소 지식은 짧고 최신인 지침 파일에 두고, 반복 적용 정책은 스킬로, 반드시 지켜야 할 규칙은 훅과 테스트로 강제한다. 병렬 세션은 서로 다른 파일을 다룰 때만 분리된 worktree에서 시작한다.

### 4. Test

에이전트가 구현하는 동안 테스트·빌드·시각 비교를 반복할 수 있게 한 명령으로 제공한다. 버그 수정은 실패 테스트를 먼저 고정하고 코드만 바꾸도록 보호한다. 에이전트 설정 자체도 실제 과제를 사용한 eval suite로 회귀 검사한다.

### 5. Deploy

AI 리뷰는 버그, 보안, 명세·계획 준수를 반복적으로 검사하고 심각도를 붙인다. 그러나 리뷰 모델이 스스로 승인하지 않으며, 중요 변경은 코드 소유자와 릴리스 책임자의 게이트를 통과한다. CI 안의 에이전트는 샌드박스, 짧은 수명의 최소 권한 자격증명, 환경별 도구 허용 목록을 사용한다.

### 6. Maintain

모니터링은 평균·표준편차나 관리도 같은 결정론적 규칙으로 이상을 먼저 감지한다. 위험 단계에 따라 기록, 읽기 전용 진단, PR 제안 또는 사전 승인된 롤백으로 권한을 높인다. 진단 결과는 새 `intent.md`가 되어 계획 단계로 돌아가고, 해결된 사고는 eval에 추가된다.

## 산출물과 통제 구조

| 계층 | 예시 | 목적 | 실패 시 위험 |
| --- | --- | --- | --- |
| 의도·설계 | `intent.md`, `spec.md` | 무엇과 왜를 고정 | 잘못된 문제를 빠르게 구현 |
| 구현 계획 | `plan.md` | 변경 범위·순서·검증 합의 | 큰 diff, 재작업, 검토 불가 |
| 조직 지식 | 저장소 지침, 스킬 | 규칙을 작업 문맥에 주입 | 규칙 누락·드리프트 |
| 결정론적 검사 | 테스트, 린터, 훅 | 불변조건 강제 | 에이전트 자기검증에 의존 |
| 권한 경계 | 샌드박스, allowlist, 브랜치 보호 | 행동 반경 제한 | 비밀 유출·운영 오작동 |
| 감사 증거 | commit, CI log, review, telemetry | 요청·행동·승인 추적 | 사고 원인과 책임 불명확 |

한 시스템을 원본 시스템(source of truth)으로 지정해야 한다. Jira나 ServiceNow가 원본이면 Markdown은 작업 사본이고 결과를 다시 기록한다. 저장소가 원본이면 외부 티켓은 commit SHA를 참조한다. 두 시스템을 아무 규칙 없이 동시에 원본으로 두면 상태가 갈라진다.

## 단계별 도입 전략

한 번에 자율 루프를 만들지 않는다. 안전한 순서는 다음과 같다.

1. `intent.md`, `spec.md`, `plan.md` 템플릿과 책임자를 정한다.
2. 로컬에서 실행 가능한 단일 build/test/lint 명령과 합격 기준을 만든다.
3. 저장소 지침과 정책 스킬을 버전 관리하고 회귀 eval을 붙인다.
4. 읽기 전용 CI 진단과 자동 리뷰부터 시작한다.
5. 낮은 위험의 쓰기 작업을 PR과 브랜치 보호 뒤에 허용한다.
6. 개발·스테이징·운영의 권한 등급과 승인 훅을 분리한다.
7. 롤백을 정기 연습한 뒤 운영 감지 루프를 연결한다.

## 측정 지표

속도만 보면 품질 악화를 놓친다. 단계별 선행·후행 지표를 함께 본다.

| 영역 | 선행 지표 | 후행 지표 |
| --- | --- | --- |
| Plan/Design | 최초 대화→의도, 의도→명세 시간 | 구현 후 요구 변경률, 승인 생존율 |
| Build | 첫 구현 통과율, 검토 가능한 병렬 세션 수 | 재작업 횟수, 계획과 diff 불일치 |
| Test | 첫 CI 성공률, eval pass rate | 운영 유출 회귀, 변경 실패율 |
| Deploy | 최초 리뷰 시간, 자동 해결 비율 | 배포 빈도·리드타임·복구시간·실패율 |
| Maintain | 이상→진단/의도 생성 시간 | 반복 사고율, 제안이 실제 수정으로 이어진 비율 |

동시에 품질 가드레일을 둔다. 예를 들어 병렬 세션 수를 늘릴 때 재작업률과 결함 유출률이 상승하면 생산성 향상으로 계산하지 않는다.

## 비판적으로 읽기

- 이 글은 Anthropic의 제품 플레이북이며 독립적인 비교 실험이나 통계 연구가 아니다.
- Claude 관련 파일명과 기능은 구현 예시다. 핵심 원칙은 버전 관리되는 산출물, 검증 가능한 피드백, 최소 권한, 사람의 책임이다.
- 문서 커밋 자체가 정확성이나 규제 준수를 보장하지 않는다. 승인자의 역량과 강제 통제가 필요하다.
- 자동화가 산출량을 늘리면 리뷰 병목과 경보 피로도 함께 커질 수 있다.
- 모델 기반 리뷰와 진단은 비결정적이다. 보안 경계, 배포 승인, 이상 감지는 결정론적 계층으로 보호해야 한다.
- 모든 변경에 같은 절차를 적용하면 작은 수정도 느려진다. 변경 위험에 따라 증거와 승인 강도를 조정해야 한다.
- 자동 생성된 감사 로그는 양보다 추적 가능성, 보존 기간, 개인정보 최소화가 중요하다.

## 용어 정리

| 용어 | 설명 |
| --- | --- |
| AI-native SDLC | 개발 생명주기 전체의 산출물·전달·검증·운영을 AI와 함께 재설계한 순환형 체계 |
| Committed artifact | 다음 단계의 입력이 되도록 버전 관리에 확정한 산출물 |
| Control objective | 조직이 지켜야 할 보안·품질·규제 목표 |
| Hook | 특정 행동 전후에 실행되어 허용·질문·차단을 결정하는 코드 |
| Skill | 반복 적용할 조직 지식을 조건과 절차로 구조화한 지침 묶음 |
| Eval | 에이전트 또는 그 설정이 실제 과제를 기준 품질로 수행하는지 확인하는 평가 |
| Control band | 정상 범위를 정의하고 이탈 강도에 따라 대응 등급을 정하는 경계 |
| Blast radius | 실패했을 때 영향을 받을 수 있는 시스템과 사용자의 범위 |
| DORA metrics | 배포 빈도, 변경 리드타임, 변경 실패율, 복구 시간 중심의 전달 성과 지표 |
