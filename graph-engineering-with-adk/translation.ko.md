### 설명 요약

영상은 Google의 Agent Development Kit(ADK)를 이용해 에이전트 시스템을 그래프 형태로 구성하는 기본 사고법을 소개한다. 마라톤 당일 전략을 만드는 코치를 예제로 삼아, 데이터 접근 수단이 없는 거대한 단일 프롬프트가 그럴듯한 수치를 지어낼 수 있음을 보여 준다. 이후 작업을 결정론적 함수와 추론 에이전트로 분리하고, 병렬 분기인 fan-out, 분기 결과를 모으는 join, 실행 경로를 선택하는 router를 순서대로 붙인다.

설명란은 이 구조를 “프로덕션 준비가 된 시스템”을 만드는 방법으로 표현하지만, 6분짜리 영상이 직접 입증하는 범위는 기본 그래프 구성과 호출 비용 구조까지다. 재시도, 시간 제한, 상태 영속화, 관측성, 인증·인가, 실패 복구 같은 운영 요구사항은 별도로 설계해야 한다.

#### 00:17–00:34 · 노드와 엣지

영상에서 그래프 엔지니어링은 시스템의 작업을 그래프 워크플로로 표현하는 방법이다.

- **노드(node)**: 실제 작업 단위다. LLM 에이전트일 수도 있고, 결과가 규칙으로 정해지는 일반 함수일 수도 있다.
- **엣지(edge)**: 어떤 노드가 끝난 다음 어느 노드로 이동하는지 나타내는 연결이다.
- **워크플로(workflow)**: 노드, 엣지, 시작점, 분기 및 합류 규칙을 합친 실행 정의다.

핵심은 모든 단계를 모델에게 자연어로 지시하는 대신, 실행 순서와 허용된 경로를 코드 구조로 드러내는 것이다. ADK 2.0은 이 예에서 함수 노드와 에이전트 노드를 같은 그래프 안에 배치하는 실행 기반으로 사용된다.

#### 00:34–01:22 · 마라톤 코치와 거대 단일 프롬프트의 문제

사용자는 마라톤을 어떻게 달려야 하는지 묻는다. 첫 번째 구현은 에이전트 하나의 큰 프롬프트에 날씨 조회, 코스 분석, 체력 확인과 경기 전략 생성을 모두 맡긴다. 화면의 응답은 구체적이고 자신 있어 보이지만, 이 에이전트에는 실제 날씨 API, 코스 데이터와 훈련 기록이 연결되어 있지 않다. 따라서 제시된 수치의 출처가 없고 일부 정보는 생성된 것이다.

이 장면의 기술적 교훈은 “프롬프트가 길면 반드시 환각한다”가 아니다. 실제 문제는 다음과 같다.

- 데이터 조회 단계가 코드나 도구 호출로 강제되지 않는다.
- 각 수치가 어느 출처에서 왔는지 추적할 경계가 없다.
- 중간 단계의 입력과 출력을 개별 테스트하기 어렵다.
- 특정 단계만 실제 API나 캐시로 교체할 연결 지점이 없다.
- 모델이 필요 없는 규칙 처리까지 모델 문맥과 호출 비용을 소비한다.

그래프는 이 문제를 구조적으로 줄일 수 있지만 LLM의 환각 자체를 제거하지는 않는다. LLM 노드가 받은 데이터를 잘못 해석하거나 근거 없는 조언을 만들 가능성은 여전히 남는다.

#### 01:22–01:50 · 프롬프트, 문맥, 루프, 그래프

발표자는 발전 단계를 다음과 같은 관점으로 설명한다.

| 층위 | 영상에서 강조하는 질문 |
|---|---|
| 프롬프트 엔지니어링 | 모델에 무엇이라고 말할 것인가? |
| 컨텍스트 엔지니어링 | 모델 주변에 어떤 정보와 도구를 둘 것인가? |
| 루프 엔지니어링 | 모델이 계획·행동·검사를 어떻게 반복할 것인가? |
| 그래프 엔지니어링 | 여러 작업 단위를 어떤 경로와 규칙으로 연결할 것인가? |

이는 설명을 위한 발표자의 분류이며 공인된 산업 표준이나 반드시 따라야 하는 성숙도 순서는 아니다. 실제 시스템에서는 그래프 노드 안에 에이전트 루프가 들어갈 수 있고, 모든 층위에 프롬프트와 컨텍스트 설계가 계속 필요하다.

### 01:50–02:46 · 함수와 에이전트로 만드는 최소 2노드 그래프

#### 화면 속 흐름

```text
START → fetch_conditions 함수 → advise 에이전트 → 종료
```

첫 노드는 경기 당일 조건을 가져오는 일반 Python 함수다. 이 단계는 모델을 호출하지 않으며, 온도·바람·날씨 같은 구조화 데이터를 반환한다. 두 번째 노드는 그 데이터를 읽고 페이스와 장비 조언을 생성하는 LLM 에이전트다.

화면에서 중요한 점은 함수와 에이전트가 서로 다른 종류의 외부 시스템처럼 취급되지 않는다는 것이다. 둘 다 워크플로의 노드이며 동일한 엣지 정의 안에서 연결된다. 개념적인 코드는 다음과 같다.

```python
# 축약 의사 코드: 실제 API는 공식 Codelab을 확인한다.
conditions = function_node(fetch_conditions)
advisor = agent_node(advice_agent)
workflow = START >> conditions >> advisor
```

#### 실행 결과의 의미

- 조건 조회 함수: LLM 호출 0회
- 조언 에이전트: LLM 호출 1회
- 결과: 실제 함수가 만든 조건을 입력으로 받은 조언

여기서 “비용이 없다”는 말은 함수 실행이 무료라는 뜻이 아니다. 모델 토큰 비용이 없다는 뜻이며, 실제 날씨 API 요금, 네트워크 지연, CPU와 운영 비용은 발생할 수 있다.

#### 설계 원칙

> 출력이 규칙과 데이터로 결정되는 작업은 함수에 두고, 모호한 언어 이해와 판단이 필요한 작업만 모델에 둔다.

이 분리는 테스트와 교체에도 유리하다. 예를 들어 고정된 테스트용 날씨 함수를 실제 날씨 API 어댑터로 바꿔도 전략 에이전트와 그래프 연결은 유지할 수 있다.

### 02:46–03:30 · Fan-out과 병렬 처리

마라톤 전략에는 날씨, 코스, 주자의 체력이라는 세 입력이 필요하다. 세 조회는 서로의 결과에 의존하지 않으므로 순서대로 실행할 필요가 없다.

```text
                 ┌→ fetch_weather ──┐
START ───────────┼→ analyze_course ─┼→ 다음 합류 지점
                 └→ pull_fitness ───┘
```

하나의 노드에서 여러 독립 경로를 동시에 시작하는 구조가 **fan-out**이다. 정상적인 병렬 실행이라면 전체 조회 시간은 세 작업 시간의 합이 아니라 가장 느린 분기의 시간에 가까워진다. 다만 실제 시간에는 스케줄링, 네트워크, 동시성 제한과 재시도 비용이 추가된다.

#### 정적 fan-out과 동적 fan-out

- **정적 fan-out**: 날씨·코스·체력처럼 분기 개수와 종류를 미리 그릴 수 있다.
- **동적 fan-out**: 입력을 분석한 뒤 조사할 하위 질문 수가 정해지는 것처럼, 실행 시점에 분기 폭이 결정된다.

영상은 두 번째 경우 ADK 2.0의 동적 워크플로를 사용할 수 있다고 설명한다. 동적이라는 말이 무제한 실행을 허용한다는 뜻은 아니다. 최대 분기 수, 깊이, 호출 예산, 시간 제한과 종료 조건은 코드로 제한해야 한다.

### 03:30–03:45 · JoinNode로 결과 모으기

```text
fetch_weather ──┐
analyze_course ─┼→ JoinNode → 묶인 입력
pull_fitness ───┘
```

JoinNode는 연결된 선행 분기가 모두 끝날 때까지 기다리는 합류 장벽이다. 가장 느린 분기가 완료되면 각 결과를 선행 노드 이름으로 구분한 사전 형태의 데이터로 묶어 다음 노드에 넘긴다.

JoinNode가 하는 일과 하지 않는 일을 구분해야 한다.

| 수행 | 기본적으로 수행하지 않음 |
|---|---|
| 모든 선행 분기의 완료 대기 | 서로 충돌하는 값을 의미적으로 조정 |
| 결과를 노드별로 구분해 묶기 | 여러 문서를 하나의 자연어 보고서로 요약 |
| 다음 노드에 하나의 입력으로 전달 | 실패한 분기의 재시도 정책을 자동 설계 |

즉 단순한 묶음에는 별도 LLM 집계기가 필요 없지만, 도메인별 병합·검증·충돌 해결이 필요하면 결정론적 집계 함수나 별도 에이전트를 추가해야 한다.

### 03:45–05:20 · Router 패턴

날씨가 더운 날, 추운 날, 보통인 날에 서로 다른 전략 전문가를 실행한다고 가정한다. JoinNode 다음의 router는 현재 데이터를 보고 세 경로 중 하나를 선택한다.

```text
JoinNode → route_by_weather ─┬→ hot_strategy
                             ├→ normal_strategy
                             └→ cold_strategy
```

#### 03:45–04:17 · LLM router

LLM router는 사용자가 자유 형식 문장으로 요청하고, 코드가 읽을 수 있는 충분한 구조화 신호가 없을 때 모델로 의도를 분류하는 방법이다. 새로운 표현이나 경계가 흐린 범주를 다루기 쉽지만 다음 비용이 있다.

- router 자체가 토큰과 지연을 소비한다.
- 같은 입력에도 결과가 달라질 수 있다.
- 허용하지 않은 경로명이 나올 수 있으므로 스키마 검증과 기본 경로가 필요하다.
- 프롬프트 인젝션이나 모호한 요청을 정책 결정으로 곧바로 연결하면 위험하다.

영상 자막의 약 04:31에 표시되는 `free tax request`는 문맥상 `free-text request`, 즉 자유 텍스트 요청을 잘못 인식한 것으로 판단된다.

#### 04:17–04:50 · 결정론적 router

선택지가 닫혀 있고 데이터에 판별 신호가 있으면 일반 조건문이 적합하다. 마라톤 예제에서는 온도 값을 읽어 `HOT`, `NORMAL`, `COLD` 가운데 하나를 선택한다.

```python
# 의미만 보존한 의사 코드
if temperature >= hot_threshold:
    route = "HOT"
elif temperature <= cold_threshold:
    route = "COLD"
else:
    route = "NORMAL"
```

이 방식은 같은 입력에 같은 결과를 내므로 단위 테스트가 쉽고 모델 호출이 없다. 다만 임계값이 실제 안전 기준을 대표하는지, 단위가 화씨인지 섭씨인지, 누락값과 경계값을 어떻게 처리할지는 별도 계약으로 정해야 한다.

#### 04:50–05:20 · 전체 호출 비용 계산

이 예의 실행 경로는 세 개의 병렬 함수, JoinNode, 결정론적 router와 선택된 전략 에이전트 하나로 구성된다. 실제 LLM 호출은 마지막 전략 에이전트의 1회뿐이다. 영상의 구두 설명은 비용을 셀 때 router를 별도로 열거하지 않지만, 앞에서 추가한 router는 그래프에 존재하며 모델을 호출하지 않는 노드로 이해해야 한다.

“한 번의 호출”은 이 데모 구성의 결과이지 그래프 워크플로의 보편적 특성이 아니다. 여러 에이전트 노드를 실행하거나 에이전트가 내부에서 모델을 반복 호출하면 호출 수는 늘어난다.

### 05:20–06:09 · 정적 그래프와 동적 워크플로 선택

발표자는 첫 판단 질문으로 “실제 입력이 오기 전에 작업 흐름을 그릴 수 있는가?”를 제시한다.

| 조건 | 권장 출발점 | 예시 |
|---|---|---|
| 노드와 경로를 사전에 알 수 있음 | 정적 graph workflow | 승인 흐름, 고정 문서 처리 단계, 날씨별 전략 분기 |
| 분기 수나 깊이가 입력에 따라 달라짐 | dynamic workflow | 조사 질문 분해, 입력 개수만큼 병렬 처리, 제한된 재귀 탐색 |
| 단순한 직렬·병렬·반복이면 충분함 | 더 작은 사전 구성 워크플로 검토 | 간단한 순차 처리나 고정 반복 |

동적 워크플로에서도 “모델이 마음대로 모든 경로를 만든다”로 이해하면 안 된다. ADK의 동적 노드에서는 일반 Python 제어 흐름이 어떤 하위 노드를 실행할지 결정할 수 있다. 모델이 하위 질문을 제안하더라도 실제 실행 한도와 권한은 코드가 가져야 한다.

연결된 Codelab은 영상보다 넓은 세 가지 축을 제시한다.

1. **Graph workflow**: 미리 그린 그래프가 다음 실행을 정한다.
2. **Collaborative agents**: 알려진 팀 안에서 LLM이 필요한 전문가를 선택한다.
3. **Dynamic workflow**: Python 코드가 런타임에 실행 모양을 정한다.

이 셋은 서로 배타적이지 않다. 정적 그래프의 한 노드가 협업 에이전트를 호출하거나, 협업 에이전트가 범위가 제한된 동적 조사를 시작할 수 있다.

## 화면 속 전체 그래프 읽기

영상의 최종 정적 그래프를 실행 책임 기준으로 다시 쓰면 다음과 같다.

```text
                              ┌─────────────────────────────┐
                              │ 결정론적 영역                │
                              │                              │
                 ┌→ 날씨 조회 ─┐                            │
사용자 입력 → START→ 코스 분석 ─┼→ Join → 온도 규칙 Router ─┼─┐
                 └→ 체력 조회 ─┘                            │ │
                              └─────────────────────────────┘ │
                                                            │
                              ┌─────────────────────────────┐ │
                              │ LLM 추론 영역                │◀┘
                              │ 선택된 전략 에이전트 1개     │
                              └──────────────┬──────────────┘
                                             ↓
                                         경기 전략
```

이 그림에서 중요한 보안·운영 경계는 router 앞뒤다. LLM은 조언의 내용을 만들지만 어떤 전문가를 실행할지 결정하는 권한은 온도 규칙을 가진 함수에 있다. 그러나 전략 에이전트에 위험한 도구 권한을 부여하면 그래프만으로 안전이 보장되지 않는다. 노드별 최소 권한, 입력 검증, 출력 정책 검사와 감사 로그가 추가로 필요하다.

## 핵심 주장 검토와 정정

| 영상의 요지 | 유효한 범위 | 한계와 더 정확한 표현 |
|---|---|---|
| 거대 단일 프롬프트가 데이터를 지어냈다 | 도구와 원본 데이터가 없는 데모 실행에서 확인된다. | 긴 프롬프트가 언제나 환각한다는 증명은 아니다. 데이터 접근과 출처 검증이 강제되지 않은 것이 핵심 문제다. |
| 개선책은 더 좋은 프롬프트가 아니라 구조다 | 실행 순서, 데이터 출처와 테스트 경계를 코드로 고정할 때 효과적이다. | 구조와 좋은 프롬프트는 대체 관계가 아니다. LLM 노드 내부에는 여전히 프롬프트·컨텍스트 설계가 필요하다. |
| 그래프가 신뢰도를 높인다 | 허용 경로와 결정론적 단계를 명시해 실행 이탈을 줄인다. | LLM의 사실 오류, 잘못된 API 데이터와 잘못 설계된 규칙까지 자동으로 해결하지 않는다. |
| 함수 노드는 비용이 없다 | LLM 토큰 호출이 없다. | 외부 API, 네트워크, 컴퓨팅과 운영 비용은 남는다. |
| JoinNode에는 병합기가 필요 없다 | 단순히 노드별 결과를 묶는 작업에는 맞다. | 의미적 통합, 중복 제거와 충돌 해결에는 별도 코드나 에이전트가 필요하다. |
| 열린 입력에는 LLM router가 가장 적합하다 | 규칙으로 열거하기 어려운 자연어 의도 분류에 유용하다. | 전용 분류기, 검색, 임베딩, 규칙과 LLM을 조합한 방식이 더 안전하거나 저렴할 수 있다. |
| 전체 그래프가 LLM 한 번으로 동작한다 | 영상의 최종 예에서는 전략 노드 하나만 모델을 호출한다. | 그래프 자체가 호출 수를 하나로 제한하지 않는다. 구성에 따라 여러 번 호출된다. |
| 입력 전 흐름을 그릴 수 없으면 동적 워크플로를 쓴다 | 런타임 크기·깊이가 변하는 작업에 맞는 기준이다. | 최대 깊이, 분기 폭, 재시도, 비용과 종료 조건을 코드로 제한하지 않으면 폭발적으로 커질 수 있다. |
| 프로덕션 준비가 된 시스템을 만든다 | 영상은 생산형 설계의 출발점을 보여 준다. | 영상만으로 영속성, 재시도, 관측성, 보안, 배포와 장애 복구가 완성되지는 않는다. |

## 기술 용어 정리

| 용어 | 한국어 설명 |
|---|---|
| ADK | Agent Development Kit. Google의 코드 중심 에이전트 개발 도구 모음이다. 이 영상은 ADK 2.0의 그래프 워크플로를 사용한다. |
| Graph Engineering | 함수·에이전트 등의 작업 단위를 노드로 만들고 실행 순서, 분기, 합류와 한계를 엣지 및 코드 계약으로 설계하는 접근이다. |
| Orchestration | 여러 작업의 순서, 병렬성, 데이터 전달, 분기와 종료를 조정하는 일이다. |
| Node | 그래프의 실행 단위다. 함수, 도구, 에이전트, join 또는 하위 워크플로가 될 수 있다. |
| Edge | 한 노드의 완료나 route 값이 다음 어느 노드를 활성화하는지 나타내는 연결이다. |
| Deterministic function | 같은 입력과 같은 외부 상태에서 예측 가능한 결과를 내도록 코드로 정의한 함수다. |
| Agent node | 언어 이해, 모호한 판단 또는 생성을 위해 LLM을 실행하는 노드다. |
| Fan-out | 하나의 선행 지점에서 여러 독립 분기를 시작하는 패턴이다. |
| Fan-in / Join | 병렬 분기의 결과가 하나의 지점으로 모이는 패턴이다. |
| JoinNode | 모든 선행 분기를 기다린 뒤 결과를 노드별로 묶는 ADK 워크플로 노드다. |
| Router | 입력 데이터나 모델 판단을 route 값으로 바꾸어 다음 경로를 고르는 노드다. |
| Closed set | 가능한 선택지를 사전에 열거할 수 있는 문제다. 명확한 데이터 신호가 있으면 결정론적 router에 적합하다. |
| Open set | 입력 표현이나 범주를 모두 미리 열거하기 어려운 문제다. LLM router를 고려할 수 있지만 검증이 필요하다. |
| Static workflow | 노드와 주요 엣지를 실행 전에 정의하는 워크플로다. |
| Dynamic workflow | 입력과 실행 결과에 따라 코드가 런타임에 하위 작업의 폭이나 순서를 정하는 워크플로다. |
| Hallucination | 모델이 근거가 없거나 사실과 다른 내용을 그럴듯하게 생성하는 현상이다. |
| LLM call | 모델 서비스에 입력을 보내 출력을 받는 한 번의 요청 또는 추론 단위다. 에이전트 한 번의 실행이 반드시 호출 한 번과 같지는 않다. |

## 버전과 재현 주의사항

연결된 Codelab은 작성 시점에 `google-adk==2.3.0`을 설치하도록 고정하며, 일부 API가 `2.0.0b1`에서도 동일하게 동작한다고 설명한다. 동시에 ADK 2.x 안에서도 `task` 모드 같은 동작 표면이 버전에 따라 달라졌음을 명시한다.

따라서 실습에서는 다음 원칙을 권장한다.

1. 설치 버전을 명시하고 잠금 파일에 기록한다.
2. 함수 노드의 입출력 스키마와 route 값 집합을 테스트한다.
3. 병렬 분기의 timeout·실패·부분 성공 정책을 작성한다.
4. LLM 호출 횟수, 토큰, 지연과 외부 API 비용을 각각 계측한다.
5. 동적 fan-out에는 최대 폭·깊이·예산과 취소 조건을 둔다.
6. 공식 Codelab 코드와 현재 설치한 ADK 문서를 대조한다.
