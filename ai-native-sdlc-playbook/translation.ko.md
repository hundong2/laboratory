## 번역 범위와 방식

이 문서는 원문의 전문을 옮긴 것이 아니다. 저작권을 존중하기 위해 원문의 큰 구조, 핵심 주장, 실행 단계, 거버넌스, 측정 방법을 한국어 학습자가 이해할 수 있도록 요약 번역하고 재구성했다. 제품 기능과 제공 상태는 2026-09-05 확인 기준이며 이후 변경될 수 있다.

## 코드는 더 이상 유일한 병목이 아니다

AI는 코드 작성 속도를 크게 높였지만 요구 수집, 승인, 검토, 보안, 배포와 운영 절차는 같은 속도로 바뀌지 않았다. 그 결과 구현 시간이 줄어들수록 앞단의 계획과 뒷단의 시험·배포가 새로운 제약이 된다. 사람이 쓴 양을 전제로 모든 줄을 같은 방식으로 검토하면 에이전트가 만든 변경량을 따라가기 어렵고, 예외를 회의와 위원회로 처리하면 거버넌스 비용도 늘어난다.

따라서 구현 단계에만 AI를 적용해서는 전체 리드타임이 충분히 줄지 않는다. 통제 목표는 유지하되 증거 생성, 정책 적용, 전달, 검증 방식까지 전체 수명주기에 맞게 재설계해야 한다.

## AI-native SDLC란

전통적인 선형 인계 대신 각 단계가 버전 관리되는 산출물을 쓰고 다음 단계가 그것을 읽는 순환형 과정이다. AI는 모든 단계에 포함되지만 사람은 판단과 승인에 대한 책임을 유지한다.

| 단계 | 전통적 경향 | AI-native 방향 |
| --- | --- | --- |
| Plan | 회의와 수작업 요구 정리 | 원천 의견에서 `intent.md` 생성 |
| Design | 요구와 설계를 별도 인계 | 정책을 적용해 한 세션에서 `spec.md` 작성 |
| Build | 코드·테스트·문서를 각각 수작업 | 계획 후 생성하고 지식은 버전 관리되는 지침으로 유지 |
| Test | 단계 경계의 QA | 구현 중 피드백과 지속 eval |
| Deploy | 모든 변경을 같은 방식으로 수동 검토 | 자동 다중 검토, 위험 변경은 사람 승인 |
| Maintain | 사람이 경보를 보고 시작 | 결정론적 트리거가 진단을 시작하고 새 의도로 환류 |

의도, 명세, 계획, 코드·테스트, 리뷰, 사고 기록의 커밋 사슬이 감사 이력이 된다. 다음 단계는 이전 단계의 승인된 산출물이 생길 때 시작한다.

## 플레이 운영 원칙

각 플레이는 변화 내용, 시작 조건, 구현 절차, 거버넌스, 성과 측정을 포함한다. 모든 플레이를 한 번에 적용할 필요는 없으며 선행 조건이 없는 항목부터 시작한다. 처음에는 사람이 각 단계를 직접 호출하고, 산출물과 게이트가 안정되면 승인된 산출물이 다음 단계를 자동으로 시작하게 한다.

## 1단계: Plan

### 의도를 `intent.md`로 포착

아이디어, 티켓 또는 운영 사고를 정형화하기 전에 제안자의 언어로 문제를 듣는다. 에이전트와 질문을 주고받아 다음 항목을 채운다.

- 해결하려는 문제와 현재 불가능한 일
- 기대하는 사용자·사업 결과
- 영향을 받는 사용자와 시스템
- 범위 밖의 항목과 제약
- 아직 답하지 못한 질문

제품 책임자가 오해를 수정하고 승인한 뒤 버전 관리되는 장소에 커밋한다. 기존 요구관리 도구가 원본이면 Markdown과 레코드 ID·commit SHA를 양방향으로 연결한다.

거버넌스 증거는 작성자, 시각, 수정 이력, 승인 또는 거절 기록이다. 측정값은 첫 대화에서 커밋까지 걸린 시간, 다음 설계로 넘어간 의도의 비율, 구현 시작 후 의도 변경 횟수다.

## 2단계: Design

### 요구와 설계를 하나의 검토 가능한 명세로

승인된 `intent.md`에 조직의 브랜드, 보안, 규제, UX 정책을 적용해 `spec.md`를 작성한다. 에이전트는 충족할 수 없는 정책 충돌과 우려 영역을 명확하게 표시해야 한다. 제품 책임자는 의도와의 일치 여부, 열린 질문의 해소 여부를 검토하고 고위험 사항은 기술·정책 책임자에게 보낸다.

정책을 작업 시점에 적용하면 몇 주 뒤 리뷰에서 처음 발견하는 일을 줄일 수 있다. 입력 의도, 결과 명세, 적용한 정책 버전과 승인 기록을 함께 남긴다. 주요 지표는 의도 커밋에서 명세 커밋까지의 시간과 구현 시작 후 명세 재작업 횟수다.

## 3단계: Build

### 계획을 먼저 승인

엔지니어는 승인된 명세를 주고 읽기 전용으로 코드베이스를 조사하게 한다. 결과 계획은 변경할 파일, 작업 순서, 위험, 대안, 완료를 입증할 테스트를 포함해야 한다. 대화를 보지 못한 다른 엔지니어도 실행할 수 있을 만큼 구체화한 뒤 `plan.md`로 커밋한다. 구현이 계획에서 벗어나면 계획도 같은 변경에 맞춰 갱신한다.

### 저장소 지침과 스킬

새 팀원이 처음 알아야 할 빌드·테스트 명령, 코딩 규칙, 구조, 반복 실수를 짧은 저장소 지침으로 둔다. 여러 저장소나 작업에 일관되게 적용할 정책은 트리거 조건을 가진 스킬로 만든다. 정책 변경은 소유자가 승인하고 실제 여러 표현의 작업에서 정상 작동하는지 시험한다.

스킬은 모델이 정책을 따르도록 돕는 조언형 통제다. 예외가 허용되지 않는 규칙에는 빠르고 범위가 좁은 훅, 린터, 테스트, 권한 규칙을 추가한다.

### 병렬 세션과 보조 에이전트

서로 다른 파일을 변경하는 독립 작업은 별도 worktree에서 병렬 실행할 수 있다. 같은 파일을 만지는 작업은 한 세션에서 순차 처리한다. 반복 검증은 도구가 제한된 보조 에이전트로 격리할 수 있다. 병렬성의 상한은 생성 능력이 아니라 한 사람이 제대로 검토할 수 있는 동시 작업 수다.

## 4단계: Test

### 자기검증 가능한 피드백 루프

빌드, 테스트, 린트, 시각 비교를 에이전트가 직접 실행할 수 있게 하고 합격 결과를 명시한다. 버그 수정에서는 실패를 재현하는 테스트를 먼저 고정하고, 수정 중 테스트를 약화하지 못하도록 보호한다. 완료 보고에는 실행한 검사와 실제 결과를 포함한다.

최종 검증을 별도 문맥에서 수행하면 구현 과정의 가정에 덜 영향을 받을 수 있다. 그러나 독립 검증만으로 충분하지 않고 구현 중 반복되는 빠른 피드백 루프가 함께 있어야 한다.

### CI의 지속 eval

에이전트 지침, 스킬, 훅, 모델이 바뀌면 실제 작업 품질도 달라질 수 있다. 최근 작업 20~50개와 수용 기준을 평가 사례로 만들고 설정 변경과 정기 일정에 실행한다. 운영 사고는 해결 후 영구적인 회귀 사례로 추가한다. pass rate 저하가 있는 설정 변경은 검토 없이 합치지 않는다.

## 5단계: Deploy

### PR 검토 루프

모든 변경에 버그, 보안, 명세·계획 준수 검토를 동일하게 적용하고 중요도와 근거를 남긴다. 스타일 잡음은 제한하고 CI가 이미 보장하는 항목은 반복 보고하지 않는다. 에이전트는 리뷰 의견을 수정할 수 있지만 자기 변경을 승인하지 않는다. 코드 소유자의 승인은 브랜치 보호로 분리한다.

### 훅을 승인 게이트로 사용

배포, 마이그레이션, 보호 경로 변경처럼 승인이 필요한 행동은 실행 전에 훅이 허용·질문·차단한다. 차단 메시지는 이유와 승인 경로를 알려야 한다. 개인이 끌 수 없는 관리형 설정으로 비밀 접근, 네트워크, 우회 옵션, 허용 도구와 확장 공급원을 제한한다.

### CI/CD 통합

먼저 실패 로그 요약이나 변경 기록 작성 같은 읽기 전용 판단부터 자동화한다. 이후 낮은 위험의 쓰기 작업을 PR 뒤에 허용한다. 에이전트 작업은 샌드박스와 짧은 수명의 최소 권한 토큰을 사용하며 운영 자격증명을 상시 보유하지 않는다. 개발, 스테이징, 운영의 자율성을 다르게 설정하고 운영은 명시적 승인 게이트를 둔다. 롤백은 자동화보다 먼저 반복 훈련한다.

## 6단계: Maintain

### 운영에서 계획으로 루프 닫기

안정적인 기준선이 있는 지표 하나를 선택하고 결정론적 스크립트로 이상을 감지한다. 예를 들어 관리도 규칙을 사용해 경미한 이탈은 기록만 하고, 중간 이탈은 읽기 전용 진단, 큰 이탈은 PR 제안이나 승인된 런북 실행으로 등급화한다.

에이전트의 진단은 이상과 증거, 기대 결과, 영향 시스템, 열린 질문을 포함한 새 `intent.md`가 된다. 담당자가 즉시 수정, 일정 등록, 기각을 결정하고 기각 결과는 탐지 규칙 조정에 사용한다. 수정이 배포되면 같은 유형의 사고를 잡는 eval을 추가한다.

탐지는 모델에 맡기지 않는다. 결정론적 감지가 먼저 발생하고 위험 등급이 에이전트가 사용할 수 있는 도구와 경로를 제한한다. 운영 변경은 정상적인 리뷰 게이트를 거치고, 롤백은 사전 승인된 경로만 사용한다.

### 정기 코드베이스 점검과 온콜

코드와 모델이 계속 변하므로 보안 점검도 정기적으로 반복해야 한다. 결과에는 검증 상태와 신뢰도를 붙이고, 수정은 기존 정적 분석과 PR 승인 절차를 통과한다. 채널이나 티켓에서 시작한 작은 수정도 같은 경로로 보내며 큰 작업은 `intent.md`로 환류한다.

## 마무리 해설

AI-native SDLC는 사람을 생명주기에서 제거하는 구상이 아니다. 사람의 주의력을 문서 작성과 반복 검사에서 의도, 위험, 예외, 운영 승인으로 이동시키는 구상이다. 성공 여부는 생성 코드량보다 다음 질문으로 평가해야 한다.

- 각 단계의 입력과 출력이 검토 가능하고 연결되어 있는가?
- 정책은 설명뿐 아니라 필요한 곳에서 기계적으로 강제되는가?
- 에이전트의 권한이 환경과 위험도에 맞게 제한되는가?
- 증거와 승인 기록을 나중에 재구성할 수 있는가?
- 운영 사고가 명세와 eval로 실제 환류되는가?

## 제품 중립적 적용 메모

원문은 Claude Code, Claude Tag, Claude Security, MCP 등 Anthropic 제품을 예로 든다. 다른 도구를 사용할 때도 다음 대응 관계를 유지하면 된다.

| 원문 역할 | 제품 중립적 요구사항 |
| --- | --- |
| 저장소 지침 파일 | 에이전트가 매 작업 읽는 짧고 버전 관리되는 규칙 |
| Skill | 조건에 따라 로드되는 재사용 정책·절차 |
| Hook | 행동 전후의 결정론적 허용·차단·승인 검사 |
| Code Review agent | 독립 문맥에서 증거와 심각도를 제시하는 검토기 |
| MCP deployment tools | 허용된 배포·상태·롤백 작업만 노출하는 도구 계층 |
| Telemetry | 누가 어떤 입력으로 무엇을 실행하고 승인했는지 남기는 추적 |
